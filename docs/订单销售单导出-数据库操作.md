# 订单销售单导出：数据库操作说明

## 1. 目的与适用范围

本文档说明“单订单销售单图片 / Excel 导出”涉及的数据库结构变更、历史数据回填、部署步骤、校验方法和异常处理。

对应 Prisma 迁移：

```text
prisma/migrations/20260726000100_order_sales_exports/migration.sql
```

数据库为 Supabase PostgreSQL。应用运行时使用 `DATABASE_URL`，Prisma 迁移使用 `DIRECT_URL`。执行前必须确认两个连接串指向同一个目标项目和环境，且不要在终端输出或提交连接串。

## 2. 数据结构变更

### 2.1 `Order` 新增字段

| 字段 | 类型 | 默认值 | 用途 |
| --- | --- | --- | --- |
| `shippingFee` | `DECIMAL(65,30)` | `0` | 销售单运费 |
| `installationFee` | `DECIMAL(65,30)` | `0` | 销售单安装费 |
| `soldAt` | `TIMESTAMP(3)`，可空 | 无 | 首次变为“已成交”的时间，即销售日期 |

### 2.2 `OrderItem` 新增字段

| 字段 | 类型 | 默认值 | 用途 |
| --- | --- | --- | --- |
| `salePrice` | `DECIMAL(65,30)`，可空 | 无 | 实际成交单价；原 `price` 继续保留为下单时参考价快照 |
| `color` | `TEXT` | 空字符串 | 销售单商品颜色 |

本次迁移只新增字段，不删除或重命名原字段。

## 3. 历史数据回填规则

迁移会执行以下回填：

1. 所有历史订单项的 `salePrice` 复制自原 `price`。
2. 历史“已成交”订单的 `soldAt` 使用该订单的 `updatedAt`。
3. 历史订单的运费、安装费默认均为 `0`。
4. 历史订单项的颜色默认留空。

注意：

- 原 `price` 为空的订单项，回填后的 `salePrice` 仍为空，管理员必须补齐后才能导出正式销售单。
- 历史订单无法准确还原首次成交时间，因此以 `updatedAt` 作为近似销售日期；可在业务核对后人工修正数据。
- 迁移完成后，管理员修改的成交价可能与原参考价不同，不能再用两列相等作为长期校验条件。

## 4. 上线前检查

### 4.1 备份与环境确认

1. 在 Supabase 确认目标项目、数据库分支和当前备份状态。
2. 生产库应先创建可恢复备份或确认时间点恢复可用。
3. 确认 `.env` 中 `DATABASE_URL` 与 `DIRECT_URL` 属于同一环境。
4. 不要在生产库执行 `npm run db:seed` 或 `prisma db push`。

### 4.2 记录迁移前基线

在 Supabase SQL Editor 执行以下只读查询，并保存结果：

```sql
select "status", count(*)
from "Order"
group by "status"
order by "status";

select count(*) as order_item_count,
       count(*) filter (where "price" is null) as null_reference_price_count
from "OrderItem";
```

如果订单量或订单项数量较大，应安排低峰期执行。迁移中的历史数据更新会写入全部 `OrderItem` 行以及全部已成交 `Order` 行。

检查 Prisma 当前状态：

```bash
npx prisma migrate status
```

存在未处理的失败迁移时，先解决失败状态，不要直接执行新迁移，也不要在未核实数据库结构前使用 `migrate resolve --applied`。

## 5. 执行迁移

在可信任的部署终端、项目根目录执行：

```bash
npm install
npm run db:deploy
npx prisma generate
npm run build
```

说明：

- `npm run db:deploy` 实际执行 `prisma migrate deploy`，只应用尚未执行的迁移。
- Prisma 会在 `_prisma_migrations` 中登记迁移；重复执行不会重复回填。
- `npx prisma generate` 使 Prisma Client 类型与新增字段同步。
- Vercel 构建只运行 `npm run build`，数据库迁移应在部署新版应用前由可信任终端执行。

推荐顺序：

1. 完成数据库备份。
2. 执行 `npm run db:deploy`。
3. 执行迁移后 SQL 校验。
4. 部署新版应用。
5. 完成订单成交及两种导出的业务冒烟测试。

## 6. 迁移后校验

### 6.1 检查迁移记录

```bash
npx prisma migrate status
```

预期：数据库结构已是最新状态，不存在失败或待执行迁移。

### 6.2 检查新增字段

```sql
select table_name, column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public'
  and (
    (table_name = 'Order' and column_name in ('shippingFee', 'installationFee', 'soldAt'))
    or
    (table_name = 'OrderItem' and column_name in ('salePrice', 'color'))
  )
order by table_name, column_name;
```

预期返回 5 个字段。

### 6.3 检查历史回填

迁移完成、业务人员尚未编辑销售数据时执行：

```sql
select count(*) as missing_sale_price_count
from "OrderItem"
where "price" is not null
  and "salePrice" is null;

select count(*) as missing_sold_at_count
from "Order"
where "status" = 'WON'
  and "soldAt" is null;

select count(*) as invalid_default_fee_count
from "Order"
where "shippingFee" is null
   or "installationFee" is null;
```

三个结果均应为 `0`。原参考价本身为空的订单项不计入第一项异常。

再将订单、订单项总数与迁移前基线比较，确认没有丢失记录：

```sql
select count(*) as order_count from "Order";
select count(*) as order_item_count from "OrderItem";
```

## 7. 应用层冒烟验证

使用一条测试订单完成以下流程：

1. 店铺管理员打开订单详情，填写成交单价、颜色、运费和安装费。
2. 保存后刷新页面，确认数据仍然存在。
3. 将订单状态改为“已成交”，确认 `soldAt` 已写入。
4. 从订单列表分别下载 PNG 和 Excel，核对商品金额与应付总额。
5. 使用有该订单查看权限的员工账号验证可导出但不可修改金额。
6. 使用无订单权限或其他店铺账号验证无法访问该订单导出接口。

可用以下只读 SQL 核对测试订单：

```sql
select "orderNo", "status", "shippingFee", "installationFee", "soldAt"
from "Order"
where "orderNo" = '<测试订单号>';

select "productName", "price", "salePrice", "color", "quantity"
from "OrderItem"
where "orderId" = (
  select "id" from "Order" where "orderNo" = '<测试订单号>'
);
```

## 8. 异常处理与回滚

### 8.1 迁移命令失败

1. 停止新版应用部署。
2. 保存完整错误信息，并查询 `npx prisma migrate status`。
3. 检查新增字段是否已部分创建、历史回填是否已部分执行。
4. 根据实际数据库状态修复迁移，不要反复手工执行同一段 SQL。
5. 只有确认失败迁移已经完整回滚或已由人工恢复后，才可按 Prisma 官方流程使用 `migrate resolve --rolled-back` 后重试。

### 8.2 新版应用异常

本次数据库变更为只增不删，旧版应用会忽略新增字段。首选回滚方式是：

1. 回滚应用版本。
2. 暂时保留新增数据库字段和迁移记录。
3. 定位问题并发布修复版本。

不要为了回滚应用而直接删除 `salePrice`、`color`、费用或销售日期字段，否则会永久丢失上线后录入的销售数据。

如果业务明确要求回退数据库结构，必须先导出新增字段数据并创建备份，再通过单独审核过的回滚迁移处理；不要直接修改 `_prisma_migrations` 或在生产 SQL Editor 临时删列。

## 9. 禁止操作

- 不得在已有业务数据的数据库运行 `npm run db:seed`。
- 不得使用 `prisma db push` 代替正式迁移。
- 不得提交 `.env`、数据库密码或完整连接串。
- 不得在未备份的情况下删除新增字段。
- 不得将失败迁移直接标记为已应用来绕过错误。
